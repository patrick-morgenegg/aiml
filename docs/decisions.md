# Decision log

Short records of choices that shape the data. Newest last. Format: context → decision → consequence.
Change a decision by adding a new entry that supersedes the old one; do not edit history.

### D-01 Full-power meets only (2026-10-10)
Squat and bench of the same meet are features (Table 1 #7, #8) and must be complete before the deadlift.
→ `EVENTS = ["SBD"]`. Deadlift-only (`D`, ~119 k), push-pull (`BD`, ~27 k) and `SD` entries with attempts in the period are excluded.

### D-02 Period 2015-01-01 … 2025-12-31 (2026-10-10)
Report 3.1 proposes 2015–2025. Full calendar years only; the running year is incomplete.
→ Parameters `DATE_MIN`, `DATE_MAX`. Extending the range needs a re-run and an update of report 3.1.

### D-03 Keep DQ and guest lifters, drop NS and DD (2026-10-10)
A `DQ` includes bomb-outs in the deadlift, i.e. failed 3rd attempts; dropping them would bias the label.
Lifters who bombed squat or bench are removed by C07 (no valid best lift). `NS` has no attempts; `DD` results
are annulled.

### D-04 Plausibility bounds (2026-10-10)
Observed entry errors: squats of 1–2 kg, deadlifts of 3 kg, ages of 3.5, jumps > 100 %. Squats of 20–25 kg
with heavy deadlifts are real ("bar squat" of injured lifters) and are kept.
→ deadlift 20–500 kg, squat 10–600 kg, bench 5–400 kg, bodyweight 20–300 kg; ages outside 5–100 → unknown.

### D-05 Jump cap 25 % (2026-10-10)
99.9 % of 3rd-attempt jumps are ≤ ~29 %, jumps > 25 % are 0.15 % of rows and dominated by entry errors.
→ `MAX_JUMP_PCT = 25`. The app rejects candidate jumps above the cap (outside the training domain).

### D-06 Deduplicate division entries (2026-10-10)
The same lifter appears once per division (e.g. Open and Junior) with identical attempts (~62 k rows).
Duplicates would over-weight these lifters. → keep the first row per name, date, federation, meet and DL1–DL3.

### D-07 Hash-based athlete split (2026-10-10)
A group split is required (report 4.1). A deterministic function of the salted athlete id gives a uniform
random draw *and* keeps every athlete in the same subset across data refreshes.
→ 70/15/15 on `int(athlete_id[:8], 16) / 16^8`.

### D-08 Default pseudonymisation salt (2026-10-10)
OpenPowerlifting is public, so recomputable ids add no new exposure; a fixed default makes runs reproducible
for everyone in the team. → `OPL_ID_SALT` optional; set a private one if required and never change it afterwards.

### D-09 Sex as segment only (2026-10-10)
Report 3.4 / 6.2. → exported with role `segment_only`; the validator and the app spec forbid it as an input.

### D-10 Full exports not in git (2026-10-10)
Parquet ≈ 48 MB, CSV ≈ 144 MB per snapshot; committing every refresh would bloat the history.
→ git contains `metadata.json` and a 5,000-row sample; full files are regenerated by the notebook
(`refresh-dataset` skill). Revisit (e.g. Git LFS or a release asset) if the app is deployed somewhere that
cannot run the notebook.

### D-11 History features from all OPL entries (2026-10-10)
`prev_best_deadlift_kg` and `prev_meets_count` use every earlier OPL entry of the athlete (any event, any year,
also outside the period), restricted to strictly earlier dates and plausible weights. They are candidates only
(report 7.3) and not part of the core feature set.

### D-12 Model monotone in the planned weight (2026-10-10)
In the data, small jumps after a good 2nd attempt fail *more* often (≈46 % at 0–2.5 % vs ≈33 % at 5–7.5 %) because
coaches choose them after a slow 2nd attempt. An unconstrained logistic regression learns this and predicts lower
risk for heavier attempts in 100 % of sampled validation situations – useless for choosing a weight.
→ Logistic regression (`notebooks/02_model_training.ipynb`) whose weight-dependent features are non-decreasing in the
planned weight and whose coefficients are constrained ≥ 0. Cost: validation PR-AUC 0.551 vs 0.555 unconstrained.
Consequence: the predicted risk is flat up to about +5 %; the app explains this limitation.

### D-13 The app suggests a weight within a coach-set limit (2026-10-10)
Supersedes the "never recommend a weight" rule of the first version of spec 08: the project owners asked for an app
that suggests the heaviest weight an athlete can attempt. With a monotone model that question is well defined for a
given risk limit. → The app suggests the heaviest allowed weight within the limit the coach sets, always next to
the full risk curve and table; it never declares a weight, and overrides are logged (report 6.3 still holds).

### D-14 Default limit: extra risk over the smallest jump (2026-10-10)
About 39 % of 3rd attempts fail, so typical lifters start at 34–45 % risk even with the smallest jump; a fixed
absolute default such as 35 % would often find no weight. → Default mode "extra risk", +5 points (presets 2 / 5 / 10);
the absolute mode defaults to the model threshold (35 %). "Close to the limit" band: ±2 points.

### D-15 Test split not evaluated yet (2026-10-10)

model. → Notebook 02 has `EVALUATE_TEST = False`; the app shows validation metrics and says the test split is unused.

### D-16 Static HTML/JS app with an exported model card (2026-10-10)
Requested by the project owners: a simple HTML and JavaScript application in its own folder. → `app/` runs without a
server or build step (also from disk); the model is a logistic regression exported as JSON and evaluated in the
browser; Node tests check it against Python reference probabilities.

### D-17 One-time test evaluation guarded by the frozen model card (2026-10-10)
The test split may be used once, with the model frozen after validation (spec 06, rule 4); a re-run of notebook 02
refits from train, so "frozen" needs a checkable definition. → The frozen model is the committed
`app/model/model.json`. Section 6 of notebook 02 refuses to evaluate unless this run reproduces it (same OPL commit,
same threshold, validation predictions within 1e-6), evaluates it once on test with the cut-offs fixed on validation
(model, B1–B3, segments) and stores the results with the date in the model card. Re-runs of the same model keep the
results and the original date; a changed model drops them with a warning. The app then shows test tables.
Consequence: set `EVALUATE_TEST = True` and run once on the snapshot `b55424f4`; record the date in a new entry here.

### D-18 Test split evaluated (2026-10-10)
Model `monotone-logreg-v1` frozen (D-17), snapshot `b55424f4` (zip SHA-256 `c5d56bb3…`, rebuilt dataset identical to

### D-19 Model v2: pre-registered selection rule and a fresh time hold-out (2026-10-25)
The test split was used once for v1 (D-18), so it cannot also pick between v1 and v2. Written down **before** any
v2 result was looked at:
- v2 is developed on train and chosen on validation only. Primary criterion: **PR-AUC on validation**.
- v2 replaces v1 only if (a) validation PR-AUC ≥ v1 + 0.005, (b) the risk never decreases with the planned weight
  (0 violations in the 2,000-situation sweep), (c) calibration stays within 2 points in every validation decile, and
  (d) every input is known to the coach at the decision point (leakage checklist, spec 05).
- Threshold rule unchanged: highest precision with recall ≥ 0.70 on validation.
- Final comparison, once: v1 and v2 on a **time hold-out** of all 2026 meets in snapshot `b55424f4`
  (`OPL_DATE_MIN=2026-01-01`, export `holdout_2026`, same cleaning rules; 81,900 attempts, 2026-01-02 … 2026-10-04).
  Reported as is, also if v2 is not better there. The 2015–2025 test split is not used for v2.

### D-20 v2 chosen and compared on the 2026 hold-out (2026-10-25)
Notebook 04, rules of D-19. Candidates on validation (PR-AUC; v1 0.551): logistic regression + new features 0.554
(+0.003, fails the +0.005 rule); gradient boosting with v1 features 0.563; **gradient boosting + new features 0.569**
(31 leaves, min. 200 per leaf, 825 trees, learning rate 0.05, monotone in `jump` and `pr_excess`). Checks: gain +0.019,
0 monotonicity violations, max. calibration gap 0.012, new inputs DL1 weight/result and number of earlier meets
(leakage checklist passed). Threshold 0.3496 (recall ≥ 0.70 on validation).
2026 hold-out, evaluated once 2026-10-25 19:02 UTC (81,900 attempts, 39.9 % failed): v1 precision 0.49 / recall 0.72 /
PR-AUC 0.56; **v2 0.50 / 0.72 / 0.58**; same order for athletes never seen in training (24,500 attempts).
→ v2 is the better model. (Taken over into the app by D-21.)

### D-21 The app runs v2; features rounded to 9 decimals before the trees (2026-10-25)
- The Third Attempt Planner now runs v2. New inputs: 1st attempt weight and result, number of earlier competitions
  (any event, 0 for a first competition). Same attempt rules as for DL2 (DL1 ≤ DL2; after a good DL1 the 2nd attempt
  must be heavier). Notebook 04 (section 6) exports the trees to `app/model/model.json` + `model-data.js` and
  40 reference cases; `js/model.js` evaluates them. v1 stays as `app/model/model_v1.json` (+ `reference_cases_v1.json`,
  still tested); notebook 02 writes only that file now, notebook 03 reads it.
- Why rounding: mathematically equal ratios (e.g. 125/54.1 and 250/108.2) differ in the last bit, some of the 825
  trees split exactly between them, and numpy and the browser's `Math.log` round the last bit differently. Without
  rounding, 2 of 40 reference cases differed by up to 0.004. The deployed rule is `floor(x · 1e9 + 0.5) / 1e9` for every
  feature, in notebook 04 and in `js/model.js`; the trees are unchanged (not refitted). Stable under ±1 ulp in 100 %
  of validation rows; Python and JS now agree to 1e-9.
- Effect, validation only: threshold re-chosen by the same rule, 0.3496 → **0.349**; precision 0.4925 → 0.4922,
  recall 0.7000, PR-AUC 0.5693 → 0.5691; D-19 checks still hold (gain +0.018, 0 monotonicity violations, calibration
  gap 0.013).
- The 2026 hold-out was re-run once for this deployed variant (nothing chosen on it): v2 precision 0.4996 / recall
  0.7190 / PR-AUC 0.5819 (before rounding 0.5002 / 0.7192 / 0.5821; v1 0.4926 / 0.7159 / 0.5622). Both runs are in
  `models/model_v2_card.json` (`holdout_2026`, `holdout_2026_history`); rounded to two decimals nothing changes.
